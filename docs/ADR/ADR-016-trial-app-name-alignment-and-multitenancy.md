# ADR-016: Trial-App Identifier Alignment + Multi-Tenant Sandbox

## Status

Proposed (2026-05-11). Closes a gap that was not made explicit in
ADR-013 — that decision wired the *routing* between genasis and the
trial-app, but said nothing about the *identifiers* (team name, channel
names, project name) flowing through that route.

## Context

Today `genasis init --trial` writes a `genasis.toml` whose Plane and
Mattermost identifiers are hard-coded to the literal strings `"trial"`
and `"trial-demo"`, regardless of what the user actually wants their
agentic team to be called:

```toml
[project]    name = "trial-demo"
[plane]      workspace_slug = "trial"
[mattermost] team_name = "trial"
```

The trial-app sim (`agents-pool/trial-app/db/sim.ts`) is reactive —
`ensureProject(slug)` lazily creates whatever slug arrives — but it has
**no per-team isolation**. All `genasis init --trial` users share one
SQLite namespace at `https://mmplane-trial.realstory.blog`, so
concurrent demos overwrite each other's kanban cards and chat threads.

Symmetrically, the real-mode template (`agents/genasis.toml.tera`)
declares `[mattermost].team_name` and `[plane].workspace_slug`, but
**not** the channel names or the human-readable project name. The
"#scrum-{project_name}" convention from ADR-014 lives only as
boilerplate inside agent prompts, never as data the CLI or trial-app
can read.

Result: three integration gaps —

1. **Identifier loss** — the user's team/project name vanishes between
   `genasis init` and what the agents see. In trial mode they see
   "trial"; in real mode they see "#scrum-{project_name}" rendered
   from a single field with no channel-list awareness.
2. **No bootstrap** — there is no way for `genasis init` to tell the
   trial-app "this team exists and these are its starting channels."
3. **No tenancy** — even if (2) existed, the trial-app could not tell
   one user's `marketing` project from another's.

Until all three are closed, the trial-mode workflow violates the
North Star (CLAUDE.md §Core Philosophy §3): a new team running
`genasis init --trial` does not see *their* team in the demo, just a
shared scratchpad with the literal name "trial".

## Decision

Three coordinated changes, shipped together because each one is
useless without the others.

### 1. Real-mode schema gains explicit channel + project-name fields

`PlaneConfig` and `MattermostConfig` in
`crates/genasis-core/src/config.rs` extend to:

```rust
pub struct PlaneConfig {
    pub url: String,
    pub flavor: String,
    pub workspace_slug: String,
    pub project_id: Option<String>,
    /// Human-readable project name, displayed in Plane UI and trial-app
    /// kanban headers. Falls back to `project.name` when absent.
    pub project_name: Option<String>,
}

pub struct MattermostConfig {
    pub url: String,
    pub flavor: String,
    pub team_name: String,
    /// Channels provisioned for this team. The first channel with
    /// `key = "scrum"` is the binding-stakeholder channel (ADR-014).
    pub channels: Vec<MattermostChannel>,
}

pub struct MattermostChannel {
    /// Stable key used by agents and templates ("scrum", "design",
    /// "design-incoming"). Must be unique per team.
    pub key: String,
    /// Mattermost channel slug. Defaults to "{key}-{project_slug}".
    pub name: String,
    /// Human-readable display name shown in Mattermost UI and the
    /// trial-app sidebar.
    pub display_name: String,
}
```

Both new fields are `#[serde(default)]` so existing `genasis.toml`
files keep loading; missing values are filled by a `Config::derive_defaults()`
pass that synthesises `project_name = project.name` and a single
`scrum` channel from `team_name + project.name`.

The TOML representation uses an inline-table array to keep
serde-toml round-tripping deterministic regardless of section order:

```toml
[mattermost]
url = "https://mm.example.com"
team_name = "marketing"
flavor = "auto"
channels = [
  { key = "scrum",          name = "scrum-marketing-squad",          display_name = "Marketing Squad — Scrum" },
  { key = "design",         name = "design-marketing-squad",         display_name = "Marketing Squad — Design" },
  { key = "design-incoming", name = "design-incoming-marketing-squad", display_name = "Marketing Squad — Design Incoming" },
]
```

### 2. `[trial].team_token` as the multi-tenant key

`TrialConfig` adds:

```rust
pub struct TrialConfig {
    pub enabled: bool,
    pub url: String,
    pub shared_secret: String,
    /// Per-team isolation key. Random 32-char hex generated by
    /// `genasis init --trial`. The trial-app uses it to scope all
    /// sim_* rows so concurrent users on the hosted instance do not
    /// overwrite each other's sandbox.
    pub team_token: Option<String>,
}
```

Empty / missing `team_token` resolves to the literal `"default"` on
the trial-app side, preserving legacy single-tenant behaviour for
configs that pre-date this ADR.

`genasis init --trial` generates a fresh token (16 bytes hex via
`getrandom`) and writes it into the config alongside the user's
chosen project name and channel list.

### 3. Trial-app sim becomes team-scoped + gains a bootstrap route

The trial-app sim schema migrates from `user_version = 1` to `2`:

```sql
-- sim_projects, sim_channels, sim_issues, sim_posts each gain:
team_token TEXT NOT NULL DEFAULT 'default'

-- and the legacy single-column UNIQUE on slug/name is replaced with:
UNIQUE(team_token, slug)   -- sim_projects
UNIQUE(team_token, name)   -- sim_channels

-- new table
CREATE TABLE sim_teams (
  token        TEXT PRIMARY KEY,
  project_slug TEXT NOT NULL,
  project_name TEXT NOT NULL,
  created_at   TEXT NOT NULL DEFAULT (datetime('now'))
);
```

The migration is performed by a small `migrate(db)` function gated on
`PRAGMA user_version`. Pre-existing rows are reassigned to
`team_token = 'default'` so the live hosted demo continues to work for
clients that never send a team header.

A new route — `POST /api/trial/bootstrap` — accepts:

```json
{
  "team_token": "a3f9b2c1e8d4...",
  "project":  { "slug": "marketing-squad", "name": "Marketing Squad" },
  "channels": [
    { "key": "scrum", "name": "scrum-marketing-squad", "display_name": "Marketing Squad — Scrum" }
  ]
}
```

…and idempotently calls `ensureTeam`, `ensureProject`, `ensureChannel`
under that team_token. Re-bootstrapping with the same payload is a
no-op; conflicting payloads update display names but never delete
existing issues or posts.

All Plane / Mattermost bridge routes resolve the active team via
(in order): `X-Genasis-Team-Token` header → `?team=` query string →
fallback `"default"`. The fallback exists so the legacy "click and
play" demo — opened by an anonymous browser tab without any token —
still works.

## Consequences

**Easier**:
- `genasis init --trial --name "Marketing Squad"` produces a sandbox
  whose kanban actually says "Marketing Squad" and whose chat shows
  "#scrum-marketing-squad" — matching what the agents will call it.
- Real-mode (non-trial) projects gain a structured channel list, so
  agents stop deriving names from string-formatting `project.name`
  and start reading them from config. This makes "rename a channel
  without rename-storm" a config edit, not a search-and-replace.
- Multiple developers can demo the trial app concurrently without
  stomping on each other.

**Harder**:
- One trial-app schema migration (V1 → V2) requires a one-time
  table rebuild; the operator deploy kit's `start.sh` runs it on
  startup and does NOT delete the legacy `default` namespace, so no
  visible data loss. Operators who want a clean slate can
  `rm data/trial.db` as before.
- Adding `MattermostChannel` is a breaking shape change for any
  external code that deserialises `MattermostConfig` with `deny_unknown_fields`.
  Internal callers do not — checked by the existing config round-trip
  test.

**Foreclosed**:
- Channel definitions cannot live in two places. Templates that
  hard-code "#scrum-{project_name}" get rewritten to look up the
  channel by `key = "scrum"` from `MattermostConfig.channels`.
  Downstream effect: `agents/env.agents.tera` emits
  `MM_SCRUM_CHANNEL_KEY` rather than the implicit
  `MM_SCRUM_CHANNEL_ID` whose value depended on a separate
  bootstrap step.

## Verification

- Unit tests:
  - `crates/genasis-core/src/config.rs`: `derive_defaults_*` series
    covering missing project_name, missing channels, single-channel
    fallback to `"scrum"`.
  - `crates/genasis-cli/src/cmd_init.rs`: `run_trial` writes the
    expected token + channel list under `--probe-only`.
- Trial-app:
  - SQL migration test: starting from a fixture V1 DB, running
    `migrate()` yields a V2 DB with `team_token = 'default'` on every
    legacy row.
  - Bootstrap route: idempotent on second call, scopes correctly when
    two distinct tokens are used in sequence.
- E2E (`#[ignore]`-gated against a live trial-app):
  `crates/genasis-providers/tests/trial_factory_e2e.rs` extends to
  also exercise team-token scoping.
